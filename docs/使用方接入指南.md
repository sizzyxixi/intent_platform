# 使用方接入指南

这份文档写给要接入本平台的 AI / Bot / 业务系统，以及帮它完成环境配置的人。运营如何配置意图、知识和工具，见《运营方配置手册》。字段细节以 `openapi.yaml` 为准。文中的 `ipk_xxx` 只表示 Key 的格式，不是能用的密钥。

## 零、先读：这个平台是什么

**平台是什么。** 这是一个按业务空间集中管理「意图、知识、工具」的配置中心。每个空间有自己的分类树、意图（描述、例句、槽位、处理方式）和识别 / 兜底设置。知识库和工具全平台共用，意图按需要引用它们。

**对你（使用方）的作用。** 用户说了一句话之后，你向平台拉取该空间的运行时配置，必要时再检索知识。配置会告诉你：这句话可能属于哪个意图、还缺哪些信息、该用哪句追问、该查阅哪些知识、该调用哪个工具、参数怎么填，以及命中后按哪种处理方式执行。对话、识别、调用和回复都由你完成。

**边界（平台不会替你做的事）：**

- 不和终端用户直接对话。
- 不保存多轮对话状态。当前意图、已填槽位、澄清次数由你记在自己的会话里。
- **没有识别接口**（开放接口里没有 `/recognize` 之类的路径）。你用下发的 `description`、`examples` 和 `recognition` 里的阈值，在自己一侧打分。控制台的单句测试只供运营自查，结果带 `simulated: true`，不代表线上效果。
- **不替你执行业务工具。** 你在自己的环境按规格调用 CLI / HTTP / MCP / 工作流。业务工具的凭据也在你这边。开放接口没有「代调用」；控制台「测试调用」是给运营用的登录会话接口。
- **没有空间级运行时业务参数。** 平台不会为空间预置店铺 ID、仓库 ID 这类值。工具需要的业务标识，由你从自己的会话上下文注入，或按槽位追问、按常量取值。某个空间里出现这类参数，只是该工具的入参，不是所有空间的初始化步骤。
- 使用方只需要只读 API Key（`意图:读`、`知识:读`、`工具:读`），不能改配置。把已有工具绑到意图是运营（或持有 `意图:写` 的维护型 AI）的工作；注册新工具还需要 `工具:写`。见《运营方配置手册》。

角色关系：

```
终端用户  ←——对话——→  你（Bot / 智能体）
                           │
                           ├── 拉配置 / 查知识 ──→  本平台
                           │
                           └── 执行业务工具   ──→  业务系统（CLI / HTTP / MCP / 工作流）
```

生产环境：

- 控制台：`http://intent.47.86.15.93.sslip.io`
- **推荐 API 基址**（按 IP 访问）：`http://47.86.15.93/intent-platform`
  - API：`http://47.86.15.93/intent-platform/api/v1`
  - MCP：`http://47.86.15.93/intent-platform/mcp`（`POST`，JSON-RPC 2.0）
- 备用主机与控制台同域：`http://intent.47.86.15.93.sslip.io`（API `/api/v1`，MCP `/mcp`）。若该主机返回 HTTP 500 且响应体为空，多半是调用方网络无法解析 `*.sslip.io`，请改用上面的 IP 路径，不要重试同一个主机名。

意图类接口带 `X-Space-Id`（或 `?space=`）；不传时用 Key 绑定的第一个空间。知识库和工具接口是全局的，不需要空间头。鉴权：`Authorization: Bearer ipk_…`。

## 一、API Key 与初始化

这一节对任何业务空间都一样。做完再处理用户请求。

1. **向运营要一把只读 API Key。** 管理员在控制台「工具中心 › 接入与密钥」创建，绑定你要服务的空间，权限勾选 `意图:读`、`知识:读`、`工具:读`。完整 Key 只显示一次，前缀是 `ipk_`。需要往平台写配置或注册工具时，那是运营侧的事，见《运营方配置手册》。
2. **把 Key 和地址放到约定位置**，按这个顺序查找，找到第一个就用，不要再往下搜：
   - 环境变量 `INTENT_PLATFORM_API_KEY`。若已设置，同时读取 `INTENT_PLATFORM_BASE_URL`、`INTENT_PLATFORM_SPACE`。
   - 文件 `~/.intent-platform/config.json`，权限必须是 `600`：

```json
{
  "base_url": "http://47.86.15.93/intent-platform",
  "api_key": "ipk_…",
  "space_id": "<运营告知的空间 ID>"
}
```

未设置 `INTENT_PLATFORM_BASE_URL` 时使用配置文件里的 `base_url`，再缺省为上面的推荐生产地址。未设置 `INTENT_PLATFORM_SPACE` 时使用配置文件里的 `space_id`。

**两处都没有 Key：立即停止，向人要，或请运营按上面的路径创建并写入约定位置。禁止在其他目录、插件目录或项目仓库里搜索 `ipk_`。那些位置即使出现类似字符串，也不是本平台的 API Key。**

3. **自检。** 先装载配置，再请求 `GET /api/v1/spaces`。成功（200，且列表里有你要服务的空间）后再做别的调用。401 `UNAUTHORIZED` 表示没带 `Authorization: Bearer ipk_…`；401 `KEY_REVOKED` 表示 Key 已被吊销；403 `SPACE_FORBIDDEN` 表示空间不在绑定范围；403 `SCOPE_FORBIDDEN` 表示缺权限。不要换路径反复试，把结果告诉运营。
4. **准备运行时配置缓存。** 调用 `GET /api/v1/runtime-config?since_version=0`，带上 `X-Space-Id`。成功是 200，响应头有 `ETag`（形如 `"空间ID-v版本"`）。`space` 是对象 `{"id","name","bot"}`，不是字符串。把整份配置缓存下来，记下 `version`。之后用 `since_version` 做增量：版本未变返回 304，没有 body。建议定时轮询，不要每轮对话都拉；版本变了要替换缓存并清空识别缓存。
5. **准备业务工具的运行环境。** 查看配置里 `tools[]` 的类型和凭据位置。CLI 工具会给出 `cli.command_template`、`cli.login_command`、`cli.auth_env`；MCP 会给出服务地址和凭据所在的环境变量名。在这些位置备好凭据并完成登录。平台不下发第三方密钥。缺凭据时不要调用对应工具，按空间兜底 `recognition.fallback` 处理，不要向用户索要账号或 token。

自检示例：

```bash
if [ -z "$INTENT_PLATFORM_API_KEY" ] && [ -f "$HOME/.intent-platform/config.json" ]; then
  eval "$(python3 - <<'PY'
import json, os, shlex
d = json.load(open(os.path.expanduser("~/.intent-platform/config.json")))
print("export INTENT_PLATFORM_API_KEY="+shlex.quote(d["api_key"]))
if d.get("base_url"):
    print("export INTENT_PLATFORM_BASE_URL="+shlex.quote(d["base_url"]))
if d.get("space_id"):
    print("export INTENT_PLATFORM_SPACE="+shlex.quote(d["space_id"]))
PY
)"
fi
: "${INTENT_PLATFORM_BASE_URL:=http://47.86.15.93/intent-platform}"
if [ -z "$INTENT_PLATFORM_API_KEY" ]; then
  echo "未找到 API Key。请运营在控制台「工具中心 › 接入与密钥」创建，写入环境变量 INTENT_PLATFORM_API_KEY 或文件 ~/.intent-platform/config.json（chmod 600）。不要在其他目录搜索。"
  exit 1
fi
curl -sS -D - "$INTENT_PLATFORM_BASE_URL/api/v1/spaces" \
  -H "Authorization: Bearer $INTENT_PLATFORM_API_KEY"
```

## 二、按层读取分类树（推荐）

`GET /api/v1/taxonomy` 和运行时配置里的 `taxonomy.categories`，不带参数时仍返回整棵树，兼容旧用法。分类节点较多时，不要一次把整棵树拉回来（返回体过大可能被模型上下文截断）。请按层下钻：

1. 先请求 `GET /api/v1/taxonomy?max_depth=1`，只取第一层分类。
2. 每个节点都带 `id`（以及可能有的 `code`）、`has_children` 和 `child_count`。若 `has_children` 为 true，再请求 `GET /api/v1/taxonomy?parent={id 或 code}&max_depth=1`，拿到该节点的下一层。
3. 重复第 2 步，直到目标节点的 `has_children` 为 false，或已经到达该空间最末一层分类。

`max_depth` 表示**从本轮起点算起**最多返回几层，取值 1～5；不传则返回完整子树。`parent` 可以是节点的 `id` 或 `code`，传入后 `categories` 是该节点的子节点（不含自身），响应里另有 `parent` 对象描述起点。找不到该节点时返回 404 `CATEGORY_NOT_FOUND`。

同一套参数也适用于 `GET /api/v1/runtime-config`（只影响其中的 `taxonomy.categories`；带这两个参数时不会返回 304）和 MCP `list_intents`（`view=taxonomy` 时传入 `max_depth`、`parent`）。

## 三、运行时一次对话怎么走

用户每说一句话，按下面的顺序处理。多轮对话的状态（当前意图、已填槽位、待调用的工具、澄清次数）由你保存在会话里，平台不保存。

### 1. 路由意图

只使用配置里 `intents[]` 中**已启用**的意图（运行时配置只包含启用项）。用每条意图的 `description` 和 `examples` 对用户原话打分，得到 Top 候选及置信度。**平台没有识别接口**，算法由你决定。控制台的单句测试不能当作线上识别。

按 `recognition` 判定：

- Top1 ≥ `threshold` → 命中该意图，接着看它的 `handling`。
- 否则取置信度 ≥ `candidate_min` 的候选（最多 `max_candidates` 个），用 `clarify_prompt` 请用户选；没有候选 → 走空间兜底 `recognition.fallback`。
- 用户选中即命中；澄清超过 `max_clarify` 次仍不明确 → 走空间兜底。

同一会话里，若上一轮已命中且用户是在补充槽位，不要重新路由，除非用户明显换了问题。

### 2. 按处理方式执行

每条意图都有 `handling`（缺省视为 `{"mode":"tool_flow"}`）。**先看 `mode`，再决定要不要追问槽位、查知识、调工具。** 空间兜底 `recognition.fallback` 使用同一套 mode（没有 `tool_flow`）。

| mode | 含义 | 你必须怎么做 |
|---|---|---|
| `tool_flow` | 工具与知识流程（默认） | 继续下面的第 3～5 步：追问槽位、查知识、调用绑定的工具，再组织回复 |
| `handoff_human` | 转人工 | **不要**调该意图上的工具或查知识。把对话交给人工。若有 `message`，可原样或按场景告知用户后转出 |
| `fixed_reply` | 固定话术 | **不要**调工具或查知识。`replies` 至少一条；多条时选一条合适的。再看 `reply_strictness`：`paraphrase`（默认，**按意思表达**）可以改写措辞，但必须保持原意，不能增减承诺或改变结论；`verbatim`（**完全固定**）必须原样输出选中的那一条，一个字都不要改 |
| `llm_free` | 让 AI 自由发挥 | **不要**调工具或查知识。自行组织回复。若有 `prompt`，把它当作发挥边界和语气要求，不要违反 |

槽位追问超限、工具失败超限、识别或澄清超限时，同样执行 `recognition.fallback`，规则同上。

已启用的转人工 / 固定话术 / 自由发挥意图会出现在 `runtime-config.intents` 里，并带上各自的 `handling`。未匹配任何意图时，仍执行空间级兜底 `recognition.fallback`。

### 3. 检查槽位，缺了就追问

仅当命中意图的 `handling.mode` 为 `tool_flow` 时才需要这一步。

命中后，读取该意图的 `slots[]`：`name`、`required`、`ask`。空间级定义在顶层 `slots[]`（`display_name`、`type`、`options`、`default_ask`）；意图里的 `ask` 已经是合并后的有效话术。

- 从当前这句话和你保存的会话上下文里抽取槽位值。平台不提供抽取规则，按槽位 `name`、`type`、`display_name` 自行抽取。
- 必填槽位（`required=true`）没有值：用该槽位的 `ask` 向用户追问，然后等待下一轮。同一槽位追问超过 `recognition.max_slot_ask` 次 → 走空间兜底。
- `ask` 以「（不向…追问：…）」这类说明开头的，是给你或接入层填的，不要把这句话发给用户。
- 不要只看 `required`。还要看绑定工具的必填入参：若某个必填入参映射自某个槽位，而槽位仍空，就先按该槽位的 `ask` 追问（或从会话上下文补），**入参不齐不要调用工具**。

### 4. 解析绑定的工具并调用

仅当 `handling.mode` 为 `tool_flow` 时才调用工具。

意图的 `tools[]` 给出绑定：`tool`、`type`、`param_map`。到顶层 `tools[]` 按 `name` 取完整规格。

对 `param_map` 里每个入参：`source=槽位` 取对应槽位值，`source=常量` 使用 `value`，`source=上下文` 从你的会话上下文取（例如会话 ID、当前用户、当前对象 ID）。必填入参拿不到值时不调用。未映射的选填入参不传。

然后按工具 `type` 在你的运行环境执行（平台没有开放的「代调用」接口）：

| type | 怎么调用 |
|---|---|
| `cli` | 按 `cli.command_template` 把 `{参数名}` 换成入参；选填参数为空时，连同它前面的选项一起去掉；按参数数组执行，不拼 shell 字符串。凭据在 `cli.auth_env`，或预先用 `cli.login_command` 登录。`output_format=json` 时把 stdout 解析为 JSON |
| `mcp` | 按 `mcp_server` 建立连接，调用 `tools/call`；凭据按 `credentials[]` 从你环境里名为 `env` 的变量取值 |
| `http` | 按 `method` + `url` 发请求；凭据由你托管 |
| `workflow` | 按 `workflow.platform` 调用，令牌取 `workflow.auth_env`；若有 `output_mapping`，按它从工作流结果取值 |
| `skill` | `GET /api/v1/tools/{name}/skill-package` 下载 zip，按其中的 SKILL.md 执行 |
| 平台内置（`source=builtin`） | 调本平台接口，带你自己的 API Key |

`confirm_required=true` 表示会改动外部数据。调用前必须先得到确认（面向用户的场景要用户明确同意）。没有确认就不调用。工具报错或超时，最多重试 `recognition.tool_retry` 次，仍失败则走空间兜底。不要编造工具没有返回的事实。

### 5. 结合知识组织回复

仅当 `handling.mode` 为 `tool_flow` 时才使用该意图绑定的知识。

- **校验（`knowledge[].usage=validate`）**：全文已在 `validation_sets`（`chunk_id="*"` 表示整篇）。生成后逐条比对，不通过就改写，改写不了就走空间兜底。
- **参考（`usage=reference`）**：运行时配置只给引用（`kb_id` / `doc_id` / `chunk_id`），需要时再 `GET /api/v1/kbs/{kb_id}/chunks` 或 `POST /api/v1/kbs/{kb_id}/search`。跨库检索用 MCP `search_knowledge`（REST 没有跨库检索）。

把工具结果和参考知识组成对用户的回复。**除工作流的 `output_mapping` 外，平台目前不会告诉你「结果里哪一个字段对应要回答的内容」，也没有回复模板。** 根据工具的 `params`、`description`、`cli.output_description`（或 HTTP / MCP 的说明）以及参考知识来解析；解析不了就按第 6 节和第 7 节处理，不要编造。

平台目前也没有「知识未命中时」的独立配置项。查不到可用知识时，能根据已有信息作答的就直接答；不能答的，执行空间兜底。

### 6. 空间兜底（以 `recognition.fallback` 为准）

识别、澄清、追问、工具失败任一环节超限，或没有可列的候选时，执行 `recognition.fallback`。它与意图处理方式是同一套 mode（没有 `tool_flow`）：

- `handoff_human`：转人工；若有 `message`，可告知用户后转出。
- `fixed_reply`：按 `replies` 与 `reply_strictness`（`paraphrase` / `verbatim`）回复，规则同第 2 节。
- `llm_free`：自行组织回复；若有 `prompt`，当作发挥边界。

`recognition.final_action`、`final_action_label`、`final_message` 是旧字段，只为兼容已有读取方。新接入应以 `fallback` 为准，不要按 `final_action` 另写一套逻辑。对应关系仅供对照：`handoff_human` → `handoff_human`；`llm_free` → `general_assistant`；`fixed_reply` → `decline`（`final_message` 为第一条话术）。

### 7. 对终端用户怎么说（必须遵守）

面向终端用户时，**不要提及「知识库」「检索」「补进知识库」「内部规范」等内部实现概念**，也不能请用户帮忙补资料。用户只应听到答案、追问、转人工说明或已配置的话术。

查不到知识、工具没有返回、或解析不了结果时：能根据已有信息作答的就直接答，必要时说明「以官方最新规则为准」；不能答的，按该意图的处理方式或空间兜底 `recognition.fallback` 转人工、回复固定话术，或在 `llm_free` 下自行组织回复。不要编造工具或知识里没有的事实。不要向用户索要账号、密码或 token。

平台目前不会自动拦截这类措辞；这是你必须遵守的规则。

## 四、业务参数

平台不规定每个空间必须有哪些业务参数。工具要什么入参，以该工具在 `tools[]` 里的 `params` / `input_schema` 以及意图上的 `param_map` 为准。

- 来源是「槽位」的：从对话里抽取，或按 `ask` 向用户要。
- 来源是「常量」的：直接用配置里的 `value`。
- 来源是「上下文」的，以及工具必填但槽位说明「不向用户追问」的：由你的接入层从会话里注入。平台没有空间级「默认业务参数」，不会在配置里预置这些值。

读到必填入参却没有值时，向接入层或使用你的人要，不要猜测，也不要因为缺少某一个业务的参数就认为环境没配好。举例见附录。

## 五、错误处理

| HTTP | 常见 code | 你下一步 |
|---|---|---|
| 401 | `UNAUTHORIZED`（缺少 API Key）、`KEY_REVOKED` | 按第一节处理；不要到其他目录搜索 Key |
| 403 | `SCOPE_FORBIDDEN`、`SPACE_FORBIDDEN` | 不重试；说明缺权限或空间不对 |
| 404 | `INTENT_NOT_FOUND`、`KB_NOT_FOUND`、`CHUNK_NOT_FOUND`、`TOOL_NOT_FOUND`、`CATEGORY_NOT_FOUND` 等 | 重新列表查询确认 ID |
| 429 | `RATE_LIMITED` | 按 `Retry-After` 等待（每个 Key 每分钟 60 次） |
| 500 且响应体为空 | （没有 JSON `code`） | 若请求的是 `*.sslip.io` / `nip.io` 主机，是调用方网络的 DNS / 代理问题，不是平台故障。改用 `http://47.86.15.93/intent-platform`，不要对原主机重试 |

错误体为 `{code, message, details, request_id}`。也可用同一把 Key 请求 `POST {推荐 API 基址}/mcp`，只读工具为 `list_intents`、`get_intent`、`search_knowledge`、`list_tools`。完整 inputSchema 见 `AI接入说明.md`。

底线：不编造事实；写操作先确认；不向用户索要账号、密码、token；不向用户暴露内部实现；API Key 只从第一节约定位置读取；只使用已启用意图；未匹配或超限时执行 `recognition.fallback`。

## 附录：业务入参只是该工具的入参（示例，不是通用步骤）

某个空间的某个工具可能需要店铺 ID、仓库 ID、订单号或其他业务标识。那只是该工具的入参，不是所有空间的初始化步骤，平台也不会在空间上预置这些值。

例如：某个客服空间里，商品查询类工具把商品 ID 映射自槽位，把店铺标识映射自「上下文」。使用方应从自己的会话里注入店铺标识；没有商品 ID 时，按该槽位的追问话术向用户要，而不是把「配置 shop_id」当成接入平台的必做项。读到必填入参却没有值，向接入层或使用你的人要，不要猜测。
