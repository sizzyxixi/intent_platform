# 使用方接入指南

这份文档写给要接入本平台的 AI / Bot / 业务系统，以及帮它完成环境配置的人。运营如何配置意图、知识和工具，见《运营方配置手册》。文档里的 `ipk_xxx` 只表示 Key 的格式，不是能用的密钥。字段细节以 `openapi.yaml` 为准。

## 零、先读：这个平台是什么

**平台是什么。** 这是一个按业务空间管理配置的中心。每个空间里有：意图分类、意图（例句、槽位、追问话术、置信与兜底规则）、知识库，以及已登记的工具，和「某个意图绑定了哪些工具、槽位如何映射成工具入参」。

**对你（使用方）的作用。** 用户说了一句话之后，你向平台拉取该空间的配置，必要时再检索知识。配置会告诉你：这句话可能属于哪个意图、还缺哪些信息、该用哪句追问、该查阅哪些知识、该调用哪个工具，以及参数怎么填。对话、识别、调用和回复都由你完成。

**边界（平台不会替你做的事，均按当前代码核对）：**

- 不和终端用户直接对话。
- 不保存多轮对话状态。当前意图、已填槽位由你记在自己的会话里。
- 没有识别接口（开放接口里没有 `/recognize` 之类的路径）。你用下发的 `description`、`examples` 和 `recognition` 里的阈值，在自己这边打分；控制台的单句测试只供运营自查，不代表线上效果。
- 不替你执行业务工具。你在自己的环境按规格调用 CLI / HTTP / MCP，业务工具的凭据也在你这边。开放接口没有「代调用」；控制台「测试调用」是给运营用的登录会话接口。
- 使用方只需要只读 API Key（`意图:读`、`知识:读`、`工具:读`），不能改配置。注册工具、把工具绑到意图是运营（或持有 `工具:写`，绑工具还要 `意图:写` 的维护型 AI）的工作，见《运营方配置手册》。

角色关系：

```
终端用户  ←——对话——→  你（Bot）
                         │
                         ├── 拉配置 / 查知识 ──→  本平台
                         │
                         └── 执行业务工具   ──→  业务系统（CLI / HTTP / MCP）
```

读完本节后，你应能分清哪些事先问平台、哪些必须自己做。然后按顺序读：第一节完成环境初始化，第二节按一次对话走完全流程，第三节处理工具要求的业务入参，第四节看错误与兜底。附录只是流程说明，不是通用步骤。

生产环境：

- 控制台（网页）：`http://intent.47.86.15.93.sslip.io`
- **推荐 API 基址**（按 IP 访问）：`http://47.86.15.93/intent-platform`
  - API：`http://47.86.15.93/intent-platform/api/v1`
  - MCP：`http://47.86.15.93/intent-platform/mcp`（`POST`，JSON-RPC 2.0）
- 备用 API 主机（控制台同域）：`http://intent.47.86.15.93.sslip.io`（API `/api/v1`，MCP `/mcp`）。若请求该主机返回 HTTP 500 且响应体为空，多半是调用方网络无法解析 `*.sslip.io` / `nip.io`，请改用上面的 IP 路径，不要重试同一个主机名。

意图类接口带 `X-Space-Id`（或 `?space=`）；不传时用 Key 绑定的第一个空间。知识库和工具接口是全局的，不需要空间头。

## 一、初始化（环境配置）

这一节对任何业务空间都一样。做完再处理用户请求。

1. **向运营要一把只读 API Key。** 管理员在控制台「工具中心 › 接入与密钥」创建，绑定你要服务的空间，权限勾选 `意图:读`、`知识:读`、`工具:读`。完整 Key 只显示一次，前缀是 `ipk_`。需要往平台写配置或注册工具时，那是运营侧的事，见《运营方配置手册》。
2. **把 Key 和地址放到约定位置**，按这个顺序查找，找到第一个就用，不要再往下搜：
   - 环境变量 `INTENT_PLATFORM_API_KEY`。若已设置，同时读取 `INTENT_PLATFORM_BASE_URL`、`INTENT_PLATFORM_SPACE`。
   - 文件 `~/.intent-platform/config.json`，权限必须是 `600`：

```json
{
  "base_url": "http://47.86.15.93/intent-platform",
  "api_key": "ipk_…",
  "space_id": "<运营告知的空间 ID>"
}
```

未设置 `INTENT_PLATFORM_BASE_URL` 时使用配置文件里的 `base_url`，再缺省为上面的生产地址。未设置 `INTENT_PLATFORM_SPACE` 时使用配置文件里的 `space_id`。

**两处都没有 Key：立即停止，向人要，或请运营按上面的路径创建并写入约定位置。禁止在 `~/.xclaw/`、`~/.workbuddy/`、插件目录、项目仓库或其他目录里搜索 `ipk_`。那些位置即使出现类似字符串，也不是本平台的 API Key。**

3. **自检。** 先装载配置，再请求 `GET /api/v1/spaces`。成功（200，且列表里有你要服务的空间）后再做别的调用。401 `UNAUTHORIZED` 表示没带 `Authorization: Bearer ipk_…`；401 `KEY_REVOKED` 表示 Key 已被吊销；403 `SPACE_FORBIDDEN` 表示空间不在绑定范围；403 `SCOPE_FORBIDDEN` 表示缺权限。不要换路径反复试，把结果告诉运营。
4. **准备运行时配置缓存。** 调用 `GET /api/v1/runtime-config?since_version=0`，带上 `X-Space-Id`。成功是 200，响应头有 `ETag`（形如 `"空间ID-v版本"`）。`space` 是对象 `{"id","name","bot"}`，不是字符串。把整份配置缓存下来，记下 `version`。之后用 `since_version` 做增量：版本未变返回 304，没有 body。建议定时轮询，不要每轮对话都拉；版本变了要替换缓存并清空识别缓存。
5. **准备业务工具的运行环境。** 查看配置里 `tools[]` 的类型和凭据位置。CLI 工具会给出 `cli.command_template`、`cli.login_command`、`cli.auth_env`；MCP 会给出服务地址和凭据所在的环境变量名。在这些位置备好凭据并完成登录。平台不下发第三方密钥。缺凭据时不要调用对应工具，转人工或按空间的最终动作处理，不要向用户索要账号或 token。

自检示例：

```bash
if [ -z "$INTENT_PLATFORM_API_KEY" ] && [ -f "$HOME/.intent-platform/config.json" ]; then
  eval "$(python3 - <<'PY'
import json, os, shlex
d = json.load(open(os.path.expanduser("~/.intent-platform/config.json")))
print("export INTENT_PLATFORM_API_KEY="+shlex.quote(d["api_key"]))
if d.get("base_url"):
    print("export INTENT_PLATFORM_BASE_URL="+shlex.quote(d["base_url"]))
if d.get("space_id"):
    print("export INTENT_PLATFORM_SPACE="+shlex.quote(d["space_id"]))
PY
)"
fi
: "${INTENT_PLATFORM_BASE_URL:=http://47.86.15.93/intent-platform}"
if [ -z "$INTENT_PLATFORM_API_KEY" ]; then
  echo "未找到 API Key。请运营在控制台「工具中心 › 接入与密钥」创建，写入环境变量 INTENT_PLATFORM_API_KEY 或文件 ~/.intent-platform/config.json（chmod 600）。不要在其他目录搜索。"
  exit 1
fi
curl -sS -D - "$INTENT_PLATFORM_BASE_URL/api/v1/spaces" \
  -H "Authorization: Bearer $INTENT_PLATFORM_API_KEY"
```

## 二、运行时一次对话怎么走

用户每说一句话，按下面的顺序处理。多轮对话的状态（当前意图、已填槽位、待调用的工具）由你保存在会话里，平台不保存。

### 1. 路由意图

只使用配置里 `intents[]` 中已启用的意图（运行时配置只包含启用项）。用每条意图的 `description` 和 `examples` 对用户原话打分，得到 Top 候选及置信度。**平台没有识别接口**，算法由你决定。控制台的单句测试只供运营自查，不能当作线上识别。

按 `recognition` 判定：

- Top1 ≥ `threshold` → 命中该意图。
- 否则取置信度 ≥ `candidate_min` 的候选（最多 `max_candidates` 个），用 `clarify_prompt` 请用户选；没有候选 → 走最终动作。
- 用户选中即命中；澄清超过 `max_clarify` 次仍不明确 → 走最终动作。

同一会话里，若上一轮已命中且用户是在补充槽位，不要重新路由，除非用户明显换了问题。

### 2. 检查槽位，缺了就追问

命中后，读取该意图的 `slots[]`：`name`、`required`、`ask`。空间级定义在顶层 `slots[]`（`display_name`、`type`、`options`、`default_ask`）；意图里的 `ask` 已经是合并后的有效话术。

- 从当前这句话和你保存的会话上下文里抽取槽位值。平台不提供抽取规则，按槽位 `name`、`type`、`display_name` 自行抽取。
- 必填槽位（`required=true`）没有值：用该槽位的 `ask` 向用户追问，然后等待下一轮。同一槽位追问超过 `recognition.max_slot_ask` 次 → 走最终动作。
- `ask` 以「（不向…追问：…）」这类说明开头的，是给你或接入层填的，不要把这句话发给用户。
- 不要只看 `required`。还要看绑定工具的必填入参：若某个必填入参映射自某个槽位，而槽位仍空，就先按该槽位的 `ask` 追问（或从会话上下文补），**入参不齐不要调用工具**。

### 3. 解析绑定的工具并调用

意图的 `tools[]` 给出绑定：`tool`、`type`、`param_map`。到顶层 `tools[]` 按 `name` 取完整规格。

对 `param_map` 里每个入参：`source=槽位` 取对应槽位值，`source=常量` 使用 `value`，`source=上下文` 从你的会话上下文取（例如会话 ID、当前用户、当前对象 ID）。必填入参拿不到值时不调用。未映射的选填入参不传。

然后按工具 `type` 在你的运行环境执行（平台没有开放的「代调用」接口）：

| type | 怎么调用 |
|---|---|
| `cli` | 按 `cli.command_template` 把 `{参数名}` 换成入参；选填参数为空时，连同它前面的选项一起去掉；按参数数组执行，不拼 shell 字符串。凭据在 `cli.auth_env`，或预先用 `cli.login_command` 登录。`output_format=json` 时把 stdout 解析为 JSON |
| `mcp` | 按 `mcp_server` 建立连接，调用 `tools/call`；凭据按 `credentials[]` 从你环境里名为 `env` 的变量取值 |
| `http` | 按 `method` + `url` 发请求；凭据由你托管 |
| `workflow` | 按 `workflow.platform` 调用，令牌取 `workflow.auth_env`；若有 `output_mapping`，按它从工作流结果取值 |
| `skill` | `GET /api/v1/tools/{name}/skill-package` 下载 zip，按其中的 SKILL.md 执行 |
| 平台内置（`source=builtin`） | 调本平台接口，带你自己的 API Key |

`confirm_required=true` 表示会改动外部数据。调用前必须先得到确认（面向用户的场景要用户明确同意；人工值守的场景按空间知识或规则由人确认）。没有确认就不调用。工具报错或超时，最多重试 `recognition.tool_retry` 次，仍失败则澄清或走最终动作。不要编造工具没有返回的事实。

### 4. 结合知识组织回复

- **校验（`knowledge[].usage=validate`）**：全文已在 `validation_sets`（`chunk_id="*"` 表示整篇）。生成后逐条比对，不通过就改写，改写不了就走最终动作。
- **参考（`usage=reference`）**：运行时配置只给引用（`kb_id` / `doc_id` / `chunk_id`），需要时再 `GET /api/v1/kbs/{kb_id}/chunks` 或 `POST /api/v1/kbs/{kb_id}/search`。跨库检索用 MCP `search_knowledge`（REST 没有跨库检索）。

把工具结果和参考知识组成对用户的回复。**除工作流的 `output_mapping` 外，平台目前不会告诉你「结果里哪一个字段对应要回答的内容」，也没有回复模板。** 你需要根据工具的 `params`、`description`、`cli.output_description`（或 HTTP/MCP 的说明）以及参考知识来解析；解析不了就如实说明查到了什么、缺什么，不要编造。

### 5. 最终动作

`recognition.final_action`：`handoff_human` 转人工；`general_assistant` 交给通用助手；`decline` 回复 `final_message`。识别、澄清、追问、工具失败任一环节超限，都执行它。

## 三、业务参数

平台不规定每个空间必须有哪些业务参数。工具要什么入参，以该工具在 `tools[]` 里的 `params` / `input_schema` 以及意图上的 `param_map` 为准。

- 来源是「槽位」的：从对话里抽取，或按 `ask` 向用户要。
- 来源是「常量」的：直接用配置里的 `value`。
- 来源是「上下文」的，以及工具必填但槽位说明「不向用户追问」的：由你的接入层从会话里注入（例如当前店铺、当前订单、当前用户）。平台没有空间级「默认业务参数」，不会在配置里预置这些值。

某个空间的某个工具可能需要店铺 ID、仓库 ID 或其他业务标识，那只是该工具的入参，不是所有空间的初始化步骤。读到必填入参却没有值时，向接入层或使用你的人要，不要猜测，也不要因为缺少某一个业务的参数就认为环境没配好。

## 四、错误与兜底

| HTTP | 常见 code | 你下一步 |
|---|---|---|
| 401 | `UNAUTHORIZED`（缺少 API Key）、`KEY_REVOKED` | 按第一节处理；不要到其他目录搜索 Key |
| 403 | `SCOPE_FORBIDDEN`、`SPACE_FORBIDDEN` | 不重试；说明缺权限或空间不对 |
| 404 | `INTENT_NOT_FOUND`、`KB_NOT_FOUND`、`CHUNK_NOT_FOUND`、`TOOL_NOT_FOUND` 等 | 重新列表查询确认 ID |
| 429 | `RATE_LIMITED` | 按 `Retry-After` 等待（每个 Key 每分钟 60 次） |
| 500 且响应体为空 | （没有 JSON `code`） | 若请求的是 `*.sslip.io` / `nip.io` 主机，是调用方网络的 DNS / 代理问题，不是平台故障。改用 `http://47.86.15.93/intent-platform`，不要对原主机重试 |

错误体为 `{code, message, details, request_id}`。也可用同一把 Key 请求 `POST {推荐 API 基址}/mcp`，只读工具为 `list_intents`、`get_intent`、`search_knowledge`、`list_tools`。完整 inputSchema 见 `AI接入说明.md` 第 9 节。

底线：不编造工具或知识里没有的事实；写操作先确认；不向用户索要账号、密码、token；API Key 只从第一节约定位置读取；只使用已启用意图。

## 附录：抽象流程的一次走查（仅作说明）

下面用生产环境某个空间里、与「查询发货地」最接近的配置，把第二节的步骤过一遍。这是说明，不是通用步骤，也不表示平台已按「查询发货地」这个意图交付。

走查时间与数据：生产 `runtime-config` 空间 `cs`（1688 智能客服），版本 61。用户原话：「商品的发货地址是哪里」。

1. **路由。** 该空间没有名为「查询发货地」的意图，例句里也没有「发货地址」。若用平台控制台那种「对照例句计算相似度」的自测方法，最高分是「交期」0.21，低于 `candidate_min` 0.3，按配置应转人工。语义上更接近的是「信息咨询」（`B.PRE.INFO`，描述为商品参数、材质、毛重、实拍图），但它的例句同样未覆盖这句话。要支持这种问法，需要运营补意图或例句——这是配置问题，不是初始化问题。
2. **槽位。** 即便人工把这句话归到 `B.PRE.INFO`，其 `offer_id`、`question_type` 在配置里都是非必填。`offer_id` 的 `ask` 是「麻烦发一下您在看的商品链接～」，并不是「你说的是哪个商品呢？我来帮你查一下？」。按第二节第 2 步，仍应检查绑定工具的必填入参：该意图绑定 `xclaw_platform_alibaba_product_get`，`product_id` 必填且映射自 `offer_id`。没有商品标识时，应使用 `offer_id` 的 `ask` 追问，等用户补充后再调用。
3. **调用。** `param_map` 还把若干业务入参标为槽位或常量。其中需要从会话上下文提供的入参，按第三节由接入层注入，不是用户追问项。调用在 Bot 运行环境执行 `cli.command_template`；平台不会代调。运行环境未登录对应 CLI 时，不能调用。
4. **回复。** 该工具的 `output_description` 只说明返回 JSON，没有「发货地址对应哪个字段」。关联知识里，校验规则 RULE-2、参考 TOOL-7（规格/实拍）也都没有把发货地址列为要回答的字段。因此，即使工具调用成功，Bot 目前也无法从平台配置得知该如何取出地址并组织成「发货地址在 XXX」。需要运营补充知识或工具输出说明，或等平台提供输出字段映射（见《设计评估_使用方链路》）。

这次走查说明：通用流程（初始化、拉配置、按槽位追问、按 `param_map` 调工具、按知识回复）是成立的；某个具体问法能不能端到端答上，取决于该空间是否配置了对应意图、必填槽位、可执行的工具和可解析的结果说明。
