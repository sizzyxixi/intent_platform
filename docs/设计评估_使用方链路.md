# 设计评估：使用方运行时链路

> 对照目标：运营先为某个业务空间配置好意、槽位、工具和知识；Bot 事先完成环境初始化。之后用户一句话进来，Bot 按配置完成「路由意图 → 补齐槽位并追问 → 调用绑定工具 → 按知识组织回复」。
> 「商品的发货地址是哪里」只作为验收走查用例，不是平台的通用能力，也不应写进使用方主流程。
> 走查依据：代码（`backend/app/services/runtime.py`、`models.py`、`services/tools.py`、`services/intents.py`、`services/recognizer.py`、`api/v1/routes.py`、`api/admin/intents.py`、`services/tool_exec.py`）以及 2026-11-13 用只读 Key 从生产 `http://intent.47.86.15.93.sslip.io` 拉取的 `GET /api/v1/runtime-config`（空间 `cs`，`version` 61，`ETag: "cs-v61"`）。

## 结论

平台已经能把 Bot 跑通一轮对话所需的**配置**一次下发：识别阈值与兜底、已启用意图的描述和例句、槽位及追问话术、意图绑定的工具与 `param_map`、被引用工具的调用规格、关联知识（参考引用 + 校验全文）。方向与目标一致，通用骨架可用。

按验收用例把链路真正跑完，**今天做不到**。按发生顺序，断在这些地方：

1. **配置未覆盖该问法。** `cs` 没有「查询发货地」意图，也没有任何例句含「发货地址」。用平台自测识别器对「商品的发货地址是哪里」打分，最高 0.21（交期），低于 `candidate_min` 0.3，会走最终动作「转人工」。语义上最接近的是「信息咨询」（`B.PRE.INFO`），其描述和例句也不含发货地。
2. **平台不负责识别，也不保存多轮对话状态。** 没有开放的识别接口；控制台「单句测试」只给运营自测。会话记忆在 Bot 侧。
3. **就算判到「信息咨询」，追问也不会按用例里那句话发生。** 该意图的 `offer_id`、`question_type` 都是非必填，追问话术是「麻烦发一下您在看的商品链接～」。绑定工具却要求 `product_id`（映射自 `offer_id`）。只看 `required=false` 的 Bot 可能不追问，进而无法调用。
4. **调用和从结果里取出「发货地址」不由平台完成。** 开放接口没有「代调用工具」；Bot 必须在自己的环境执行 CLI / HTTP / MCP，并自行解析返回。工具只有一句笼统的 `output_description`，没有「发货地址对应哪个字段」的映射，也没有回复模板。关联知识 TOOL-7（规格/实拍）的能力列表同样不含发货地址。
5. **业务工具凭据在 Bot 运行环境。** 西之月工具需要 `xclaw-cli auth login` 或 `XCLAW_UMC_TOKEN`。平台不下发密钥；生产服务器上的 CLI 目前也未登录，控制台「测试调用」会失败。

因此：要达到用例里的效果，先要由运营补意图 / 例句 / 必填槽位和知识（配置问题）；同时平台缺少输出字段映射、槽位来源标记，也没有给使用方的工具调用接口（产品缺口）。

## 验收用例在生产上的实际走查（cs / v61）

用户原话：「商品的发货地址是哪里」。

| 步骤 | 生产上实际发生的事 |
|---|---|
| 拉配置 | `GET /api/v1/runtime-config?since_version=0` 返回 200，17 条已启用意图、4 个被引用工具、18 组校验知识。`recognition.threshold=0.6`，`candidate_min=0.3`，`clarify_prompt` 为「我想确认一下，您是想要以下哪一项？」，`final_action=handoff_human` |
| 路由意图 | 17 个意图中没有「查询发货地」。平台自测识别器（`ExampleSimilarityRecognizer`，仅对照 `examples` 与意图 `name`，不用 `description`）得分：交期 0.21、售中履约 0.16，其余为 0。全部低于 0.3，按空间设置应转人工。Bot 若改用语义模型，仍无法从配置里读到一个专门覆盖该问法的意图 |
| 最近似意图 | `B.PRE.INFO` 信息咨询。描述是「商品参数、材质、毛重、实拍图」；例句是实拍图 / 材质 / 毛重 / 详细参数。槽位：`offer_id`、`question_type`、`shop_id`，均为非必填。绑定工具：`xclaw_platform_alibaba_product_get` |
| 槽位追问 | `offer_id.ask` = 「麻烦发一下您在看的商品链接～」（来自空间槽位 `default_ask`，`ask_overridden=false`）。不是「你说的是哪个商品呢？我来帮你查一下？」。因 `required=false`，按平台槽位规则不会强制追问 |
| 工具规格 | `tools[]` 中该工具 `type=cli`，`command_template` 为 `xclaw-cli platform alibaba product get --shop-id {shop_id} --product-id {product_id} --web-site {web_site} --scene {scene} --json`。`params` 里 `shop_id`、`product_id` 必填。`param_map`：`shop_id`←槽位 `shop_id`，`product_id`←槽位 `offer_id`，`web_site`/`scene`←常量 `1688`。`confirm_required=false`。`output_description` 仅为「JSON（--json）；参数与返回以 xclaw-cli schema … 为准」，没有字段级说明 |
| 知识 | 校验：`kb_cs_reply` 的 RULE-2、`kb_cs_conf` 整篇。参考：CLOSE-2（收束：实拍/参数→现货与价→问数量）、TOOL-7（规格/实拍，能力写的是参数、毛重、实拍图、证照，成功字段为 `spec_fields` / `media_urls` / `cert_list`）、TOOL-1、TOOL-2、LEDGER-1。检索「发货地址」没有命中与发货地相关的切片 |
| 执行 | 开放接口不能代为调用该 CLI。本次未在生产实跑 `xclaw-cli`（运行环境未登录，且走查没有可用的商品 ID / 店铺 ID） |

## 分环节评估

| 环节 | 平台现状 | 是否满足 | 缺口 | 建议改造 |
|---|---|---|---|---|
| 1. 环境初始化（地址、Key、空间） | 生产地址 + API Key（`Authorization: Bearer ipk_…`）+ `X-Space-Id`。Key 由管理员在「接入与密钥」创建。约定位置为环境变量或 `~/.intent-platform/config.json`。`GET /api/v1/spaces` 可自检。与具体业务无关 | 满足 | 无结构性缺口。文档曾把某个业务的入参写进通用初始化，属于文档问题，不是接口问题 | 文档改为通用初始化即可（P0 文档） |
| 2. 意图路由 | 无开放识别接口。`runtime-config.intents[]` 提供 `description`、`examples`（无单独关键词表）。空间 `recognition` 提供 `threshold`、`candidate_min`、`max_candidates`、`max_clarify`、`clarify_prompt`（用于意图之间澄清，不是槽位追问）。控制台 `POST /api/admin/spaces/{sid}/test` 用例句二元组相似度做自测，明确不代表线上效果（`recognizer.py`） | 部分满足：语料和阈值能下发，识别算法和效果由 Bot 负责 | ① 平台不替 Bot 识别，Bot 必须自备算法。② 本用例在 cs 没有对应意图和例句，自测识别会转人工。③ 识别器不使用 `description` | 运营为要支持的问法补意图 / 例句（P0 配置）。若希望「接入即可识别、效果可评测」，再考虑开放识别接口或允许登记识别模型（P1 产品） |
| 3. 槽位 | 空间槽位：`name`、`display_name`、`type`、`options`、`default_ask`（`models.SlotDef` / `slots.to_dict`）。意图侧：`name`、`required`、`ask`（有效值经 `effective_slots` 合并）。可覆盖追问话术 | 部分满足：必填标记和追问话术存在，能驱动「缺了就问」 | ① 没有槽位来源字段（用户 / 会话上下文 / 系统注入），只能把「不向用户追问」写在 `ask` 文本里。② 没有抽取规则或抽取提示。③ 意图 `required` 与工具入参 `required` 可能不一致（本用例即是）。④ `clarify_prompt` 不能替代槽位 `ask` | 增加槽位来源（P1）。校验「必填工具入参所映射的槽位，应标为必填或声明由上下文注入」（P1）。抽取仍可由 Bot 做，需要时再补抽取提示字段（P2） |
| 4. 工具绑定与调用规格 | 绑定为 `{tool, param_map}`，`param_map` 的 `source` 为「槽位 / 常量 / 上下文」（`intents._clean_binds`）。运行时意图内带 `type`、`param_map`，MCP 另带 `server`、`mcp_tool`。顶层 `tools[]` 由 `tools.api_dict` 给出完整规格：CLI 有 `command_template`、`bin`、`auth`、`auth_env`、`login_command`、`output_format`、`confirm_required`、`input_schema` 和 `params[]`；HTTP 有 method/url；MCP 有 `input_schema`。绑定顺序即数组顺序，没有主辅或调用顺序字段。`confirm_required` 在工具定义上，不在绑定上 | 部分满足：怎么调、入参怎么拼，配置是够的 | ① 没有调用顺序 / 主辅标记（知识正文里有「主工具(按序)」，绑定结构没有）。② 上下文类入参要 Bot 自己从会话取，平台不注入。③ 开放接口不能执行工具（见第 8 行） | 可选：绑定增加顺序或角色（P2）。上下文入参保持由 Bot 供给，文档写清（P0 文档） |
| 5. 结果处理与回复 | CLI：`output_format`、`output_description`（自由文本）。HTTP/MCP：`output_example` 只在管理端 `admin_dict`，不进入 `runtime-config`。工作流才有 `output_mapping`（`from` → `as`）。没有回复模板，也没有「从结果取哪一字段再填入回复」的结构 | 不满足目标中的「查出后回复发货地址在 XXX」 | Bot 必须自己解析 JSON、自己组织句子。本用例相关工具和知识都没有指出发货地址字段 | 为工具增加面向运行时的输出字段说明或映射，并允许意图关联「如何把结果说出来」的参考知识或模板（P0 产品，否则这类问答只能靠 Bot 猜字段） |
| 6. 知识 | 意图 `knowledge[]`：`kb_id`、`doc_id`、`chunk_id`、`usage`（`reference` / `validate`）。`usage=validate` 的全文在 `validation_sets`。参考知识需 Bot 再读切片或检索。`GET /api/v1/kbs/{id}/chunks`、`POST …/search` 可用。知识库是全局的 | 部分满足：意图到知识的关联和校验规则能下发 | 参考知识只有引用，不含全文（校验才有全文）。本用例没有发货地相关知识。RULE-2 写「必填槽位：offer 或问题类型」，与运行时 `required=false` 不一致，Bot 会读到两套规则 | 需要该类回复时由运营补知识（P0 配置）。考虑对 `reference` 也下发全文或明确要求 Bot 预拉（P1）。启用校验应检查知识所述必填与槽位 `required` 是否一致（P1） |
| 7. 多轮状态 | 平台不保存会话、已填槽位或上一轮意图。`runtime-config` 是配置快照。工作流参数里的 `mode=session` 只用于部分工作流用户标识，不是对话状态 | 按当前设计，由 Bot 保存多轮状态即可，但此前未写清楚 | 若 Bot 不自己记槽位，第二轮「用户回复了具体商品」会对接不上。平台也没有会话级 API | 文档明确：多轮状态在 Bot（P0 文档）。只有在需要跨 Bot 续聊或审计对话时，再做会话存档（P2） |
| 8. 工具执行与凭据 | 平台只登记、不代执行（`tools.py` 模块说明）。真实执行仅控制台「测试调用」`POST /api/admin/tools/{name}/test`（登录会话，`tool_exec.py`），不对 API Key 开放。CLI 凭据：`cli.auth_env`（如 `XCLAW_UMC_TOKEN`）、`cli.login_command`；MCP 凭据只下发位置和环境变量名，不含密钥值 | 部分满足：规格和凭据位置够 Bot 自己执行；「把执行也交给平台」不满足 | 使用方必须在自己的环境安装并登录对应 CLI / 填入密钥。生产服务器 xclaw-cli 未登录，「测试调用」失败。平台没有空间级运行参数可预置这类业务入参 | 保持「执行在 Bot」则把初始化写进使用方文档（P0 文档）。若希望只持 Key 就能调业务工具，需新增带确认的调用接口，并解决第三方凭据托管（P1 产品，涉及安全边界） |

## 建议怎么补（按优先级）

- **P0 配置（不改代码也能让本用例往前走）：** 为要支持的问法增加意图或把例句 / 描述写入最接近的意图；把调用工具所必需的槽位标为必填（或明确由上下文注入、不向用户追问）；把追问话术写成对用户说的那句；补一条说明「从工具结果的哪个信息回答用户」的知识。
- **P0 文档：** 使用方指南只写通用的初始化与运行时步骤；业务入参从工具定义读取；写明识别和多轮状态在 Bot 侧；写明没有代调用、没有输出字段映射时 Bot 应如何处理。
- **P0 产品：** 运行时下发可用的输出说明或字段映射（至少让 Bot 不必猜「地址在哪个键」）。
- **P1：** 槽位来源；意图必填与工具必填的一致性检查；可选的识别接口或官方识别说明；可选的使用方调用接口（含确认和审计）。
- **P2：** 绑定主辅 / 顺序；参考知识全文下发；会话存档；空间级运行参数。
